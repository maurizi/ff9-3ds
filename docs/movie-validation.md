# Movie display validation

## Implemented: packed RGB24 scanout (2026-10-16)

The original movie overlay selects `DISPENV.isrgb24` for full-screen movies.
Previously both DS scanout and PC frame dumps interpreted every framebuffer as
RGB555. They now read the selected format from `psx_gpu_display_info()`.

RGB24 uses three contiguous bytes per visible pixel, with display X expressed
in VRAM halfwords, not pixels. The PSX
[framebuffer format specification](https://psx-spx.consoledev.net/graphicsprocessingunitgpu/#framebuffer)
places red in bits 0–7, green in 8–15 and blue in 16–23. The display-start
register ignores X bit 0, also observed in the DuckStation experiment below.
The DS converts each sampled RGB8 triplet to its RGB555 bitmap with opacity
set, using the existing 4/5 nearest scene sampling. Packed movie frames bypass
the text-region coverage filter. There is no new framebuffer allocation.
Full-VRAM diagnostic dumps intentionally remain raw RGB555 interpretations;
only displayed-frame dumps use the selected RGB24 format.

## PSX reference evidence

`tools/test_rgb24_psx.py` generates a disc-free PS-X EXE containing a synthetic
1 MiB VRAM upload and a small MIPS program that configures RGB24 scanout and
parks. It also runs the host build of the production pixel reader and DS
scaler. No game or BIOS bytes are generated by the fixture tool.

Compared unmodified PNG screenshots from DuckStation
`0.1-12080-g9cb25f7e9`, software rendering, against that output:

| requested VRAM origin | full RGB8 (320×240) | DS scaler RGB555 (256×192) |
|---|---|---|
| 0, 0 | all pixels exact | all pixels exact |
| 480, 240 | all pixels exact | all pixels exact |
| 1, 5 (effective X=0) | all pixels exact | all pixels exact |

The second origin exercises the other packed movie buffer. The last case caught
and fixed the ignored X bit. For each DS pixel, the comparison independently
samples the PSX PNG at `(x*5/4, y*5/4)`, truncates each channel to five bits and
compares with the production scaler's halfword output. This is host execution
of the DS scaler, not a capture from DS hardware or melonDS.

Reproduce:

```sh
tools/docker.sh make build/tests/display_rgb24_probe
python3 tools/test_rgb24_psx.py --out build/validation/movie_rgb24 --origin 480 240
# Boot the generated fixture.exe in the PSX reference emulator and capture PNG.
python3 tools/test_rgb24_psx.py --out build/validation/movie_rgb24 --origin 480 240 \
    --reference /path/to/unmodified-reference.png
```

DuckStation settings: `[GPU] Renderer=Software`; `[Display] CropMode=Borders`,
`ScreenshotMode=UncorrectedInternalResolution`, `ScreenshotFormat=PNG`.
Artifacts from this run are under ignored `build/validation/rgb24_duck_0`,
`rgb24_duck_480`, and `rgb24_duck_odd`, including generated EXEs, paired PNGs
and JSON reports. Host sanitizer tests additionally exercise row wrapping,
dimension caps, zero sizes and untouched output borders. Crossing VRAM edges
is defensive implementation coverage, not verified original-hardware parity.

The installed PCSX-Redux software `/screen/still` endpoint returned red and
blue reversed for the RGB24 fixture; its capture also clipped a deliberately
out-of-range origin. Redux OpenGL's screenshot endpoint was unavailable.
Those attempts were not treated as passing references or used to change the
port's channel order. DuckStation supplied the successful reference above.
All reference emulator processes were closed after testing.

## Implemented: bounded STR/MBG frame assembly

`port/psx/movie_stream.c` now assembles FF9's ten-sector frames: two 2048-byte
audio/metadata sectors, then eight 2324-byte video sectors with 32-byte headers
and reverse-ordered 2292-byte payloads. This follows the original overlay's
`func_8019BA70`, `func_8019BCE8`, `func_8019C434` and `func_8019C2F4`, and agrees
with the [FF9 STR format documentation](https://psx-spx.consoledev.net/dev/ps1/cdr/cdromfileformats/streaming/).
The assembler checks sector order, frame identity, dimensions, payload lengths
and duplicated BS headers. Errors latch until reset, and reset permits seeking
directly to a complete frame. It retains both camera records, control flags,
video headers and the complete padded video tail containing MBG extras.

The separate audio view validates AKAO lengths and block alignment and preserves
the original SPU pitch value. It identifies no-audio sectors and the AB-filled
terminal payload in disc-4 MBG116, rather than interpreting that marker as a
2.8-billion-byte sound block. ADPCM samples are not decoded or played yet.

`tools/movie_catalog.py` walks ISO9660 movie extents and runs the production C
assembler against every sector. Results from the user's four NTSC-U discs:

| disc | movie files | playable frames | frames with camera metadata | unused tail sectors |
|---|---:|---:|---:|---:|
| 1 | 19 | 14,141 | 745 | 10,320 |
| 2 | 14 | 8,066 | 864 | 18,850 |
| 3 | 14 | 8,404 | 493 | 16,240 |
| 4 | 10 | 12,768 | 1,861 | 0 |
| total | 57 | 43,379 | 3,963 | 45,410 |

All playable frames assembled successfully, with 320×224 dimensions, BS version
2, and continuous frame numbers from 1 through the declared end. Of those,
42,033 frames contain AKAO audio, one has terminal sound padding, and the rest
are silent. The probe validates unused ISO tail sectors separately as frame-zero
padding; it does not feed them to the assembler as playable data.

The maximum compressed BS length observed is 18,336 bytes. The largest declared
expanded MDEC run-level size is 15,104 words (60,416 bytes, before its command
word). One assembler object takes 22,708 bytes on the host: it stores compressed
video, both full audio/metadata sectors, all eight video headers and bookkeeping.
It allocates nothing internally and has no global frame buffer. Future playback
must include decoder scratch space, sound queues and peak loading overlap in its
DS budget; this object is not the entire movie working set.

Reproduce after building the probe:

```sh
tools/docker.sh make test-movie-stream build/tests/movie_stream_probe
python3 tools/movie_catalog.py '/path/to/FF9 CD1.img' --disc 1 \
    --out build/validation/movie_stream_disc1.json
# Repeat with the other three raw disc images and --disc 2/3/4.
```

This run's final catalogs are `build/validation/movie_stream_audio_disc1.json`
through `movie_stream_audio_disc4.json`. Sanitizer tests exercise reverse chunk
placement, retained camera bytes, consecutive reuse, seeking, truncated input,
inconsistent headers, invalid audio lengths, terminal padding and latched errors.
These checks establish stream framing and bounds, not decoded pixel or audio
fidelity; actual PSX movie captures remain necessary for decoder validation.

## Implemented: BS v2 coefficient expansion

`port/psx/movie_vlc.c` expands the compressed stream into the MDEC command and
run-level halfwords. Prefix groups, sign handling, escapes, DC quantization
bits and FE00 padding follow the original `func_8019AEC0` / `func_8019B00C`.
The caller supplies the user's 108 run/level pairs from `D_8019DCFC`; the
decoder neither embeds a new game-data table nor allocates a lookup buffer.
Input reads and output writes are bounded, and malformed or unsupported
streams return errors. Its output buffer can require up to 65,540 bytes under
the original 0x4000-word limit; this is additional to the compressed-frame
storage above. It performs no inverse quantization, IDCT or RGB conversion.

Verification on 2026-10-16:

* Native expansion succeeded for all **43,379 playable frames**, each producing
  the expected 1,680 blocks. Full-scan catalogs are under ignored
  `build/validation/movie_vlc_all_disc1.json` through `movie_vlc_all_disc4.json`.
* **171 frames** (beginning, middle and end of every movie) were expanded by
  FF9's original MIPS routine in PCSX-Redux, then compared byte-for-byte with
  native output, including command words and padding. All matched; the four
  bytes after each original output retained their canary value. Reports and
  paired compressed/reference/native streams are in
  `build/validation/movie_vlc_psx_disc1_ready` and `movie_vlc_psx_disc234`.
* A separate ARM9 test ROM linked with **`ds_arm9.specs`** ran in melonDS 1.1
  **original DS mode (67 MHz)**. Every synthetic prefix/sign, escape and bounds
  test passed, as did four PSX coefficient fixtures selected from the latter
  report (including its largest output and most compressed bits consumed).
  `movie_vlc_ds_done=1` and `movie_vlc_ds_failures=0` were read from the matching
  savestate. Evidence: `build/validation/movie_vlc_ds.png`, `.ml8`, and
  `movie_vlc_ds_result.json`; fixture identities are in
  `build/tests/movie_vlc_fixture.json`. This verifies the decoder component in
  DS mode, not a working original-DS build of the full game.

The original-routine comparison injects the user's unmodified ovl_64 bytes and
a small caller into a dedicated paused emulator, then restores its full state.
On a freshly paused emulator, BIOS initialization must first enable normal RAM
access; `--warmup-frames 120` performs that initialization inside the saved-state
boundary. The initial cold-RAM attempt was rejected when the original routine
failed to return; it was not counted as a passing comparison. The emulator and
X server were closed and configuration restored after verification.

Reproduce coefficient checks:

```sh
tools/docker.sh make test-movie-vlc build/tests/movie_vlc_probe
# Start the reference emulator paused; default --emu points to ../ff9-decomp.
python3 tools/test_movie_vlc_psx.py --out build/validation/movie_vlc_reference \
    --warmup-frames 120
tools/docker.sh make movie-vlc-ds VLC_REFERENCE=build/validation/movie_vlc_reference
```

Boot `build/tests/movie_vlc.nds` in DS mode. Generated fixture assembly uses
`.incbin` from ignored captures and the user's overlay; the ROM contains game
data and must not be distributed. This is a component test with fixed buffers,
not a playback benchmark. The whole-catalog scan additionally accepts
`movie_catalog.py --vlc-table PATH`, where PATH is the 216-byte slice of the
user's ovl_64 binary at file offset 0x55FC (address 0x8019DCFC).

## Still incomplete

`port/game/movie.c` still substitutes placeholder frame timing. RGB24 scanout
alone does not implement movie playback. Remaining work includes sector/frame
integration of frame assembly and coefficient expansion, original-compatible
MDEC inverse quantization/IDCT/RGB conversion, movie audio, synchronized frame
timing, skipping/end conditions, MBG camera metadata and graphics composition.
Both decoding working sets and stream buffers must fit the intended DS memory
budget. No actual movie sequence, animation video, audio synchronization or
end-to-end DS movie playback is claimed by these synthetic display checks.
